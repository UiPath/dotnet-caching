# Routing between an existing Redis client and the library

`UiPath.Caching.Migration` lets an application move a cache group between its existing Redis client (the source) and UiPath.Caching, and back, on any call, with both clients reading and writing the same Redis keys and bytes. One local tier per node serves both paths, and every write, remove and clear tells the other nodes.

## Register

```csharp
services.AddCaching(configuration, b => b.AddRedisConnection());   // the application's own stack, with its connector

services.AddCachingRouter(configuration, router => router
    .Add(new RouterCacheRegistration<Folders>
    {
        Name = "folders",
        Group = "navigation",
        Source = new FoldersSource(oldClient),          // your ISourceCache<Folders>
        RedisKey = key => $"n:folders,c:{key}",         // the exact key text the old client uses
        LocalCap = TimeSpan.FromSeconds(30),            // zero: no local copy
        DefaultExpiry = TimeSpan.FromHours(1),
    })
    .UseLibraryWhen(group => flags.IsOn(group))         // true: library path; read once per call
    .UseBypassWhen(() => settings.BypassLibrary)        // optional live kill switch, read on every call
    .UseEnvelope(new OldEnvelopeSerializer()));         // optional: ISerializerProxy<byte[]> of the old value format

var folders = provider.GetRequiredService<IRouter>().Get<Folders>("folders");
var value = await folders.GetOrAddAsync(key, token => LoadAsync(key, token), CacheExpiry.After(TimeSpan.FromMinutes(5)));
```

The router builds a Redis-only named stack on the application's connector (`AddNamedCachingOnPrimaryConnection`) with a pass-through key strategy, your envelope as the only serializer and `RemoveUnreadable = false`. The stack marks the envelope header-free (`IHeaderFreeSerializerProxy`), so it must never start a value with a byte from 0x01 to 0x1F other than tab, line feed or carriage return; a write that would fails with `InvalidOperationException`. It compiles against the public `UiPath.Caching` API only.

## Without an envelope

Leave out `UseEnvelope` when both sides of the move are library formats: a key separator change (for example `:` to `$`), or a move to a new Redis instance with the connection prefix dropped. The in-place keys then already hold the library's own format.

The router's library cache uses the library's own JSON format, and `"json"` as a write format means that JSON. The in-place side keeps the library's system fields. `UseChannelBridge` is refused without an envelope, since the bridge carries the older client's invalidations and there is no older client.

## Behaviour

- **Path.** The predicate is read once per call and an exception means the source. A call stays on one path, including the write after a factory run.
- **Local tier.** One memory cache per node, keyed by cache name and key as two fields, each entry capped per cache; it has no size limit and no bound on the number of keys within the cap. A fill is installed only if no eviction of that key and no clear of that cache happened after the read started. The local deadline is the read start plus the TTL the library reports, bounded by the cap; the source reports no TTL, so the cap alone bounds its fills.
- **Writes.** The Redis command completes, then the node evicts the key, then it publishes. A write of unknown outcome (`WriteOutcome.Unknown`) evicts and publishes at once, keeps the key off the local tier, then evicts and publishes again once the late commit can no longer land: after the longer of `PendingWindow` and the settle deadline the adapter returns with `WriteResult.UnknownWithin`. `PendingWindow` must cover the longest command lifetime of your source client; for the library path the router uses the cache timeout plus the longest command timeout of the connected multiplexer's effective configuration (async, sync and the maintenance relaxed timeout, whatever set them), read once without waiting for a connection and kept across disconnections (10 minutes until it has been read), and a configured timeout above one day fails the router at startup, and `UseLibrarySettleBound` replaces that with a value you give. A failed publish is kept once per key and retried by one worker with backoff, counted against the local cap; past 1024 waiting keys it keeps one topic invalidation for the cache instead.
- **Events.** One topic per cache (`router:{cache}`). A peer's key event evicts the key; a topic invalidation or any missed-events signal clears that cache's local entries.
- **Clear.** Publish, `ISourceCache.ClearAsync`, publish again. The scan stays with your source.
- **Outcomes.** On the library path an unavailable client runs the factory only when the source answers absent (the loaded value is then written to the source); when the source cannot answer either, the call throws `CacheUnavailableException`. An unreadable value is retried on the other client; unreadable on both is a counted miss and the key stays, but under `GetOrAddAsync` the factory result overwrites it. A write is retried on the other client only when the first reports `NotSent`. After `StopAsync` or dispose a call throws `ObjectDisposedException` before sending anything; stop waits a bounded time, then announces a cache-level invalidation; a pending key keeps its own timer and gets its final eviction and announcement at its real deadline, and the router's resources are released only after any admitted call has ended and the pending keys have settled; `StopAsync` returns after the bounded wait, `DisposeAsync` waits for the rest. Pending keys are waited for to their real deadlines, since an earlier final announcement would let a peer refill the old value and miss a commit that lands late; past `CleanupBound` one warning lists the keys still pending with their deadlines. A write of unknown outcome therefore makes shutdown slower, up to its settle window. A process killed during that wait (for example at a termination grace period) falls into the crash case: peers keep a local copy until their local cap. A write the client provably never sent is `NotSent`, so this wait follows only real unknown outcomes.
- **Cold start.** Every loaded value publishes a `Set` event to the peers, which evict the key, so a cold node's loads cost one event each.
- **Single flight.** Concurrent misses for one key on a node share one load, whichever path serves them. A caller that starts after a write, remove or clear of the key does not join an older load, and that load does not write its result if the key or cache changed while its factory ran.

The library cache must implement `IMigrationCache`; a stack whose cache does not counts as a library that failed to start (see below). On the library path reads use `IMigrationCache.ReadSnapshotAsync`: the value and its TTL come from one snapshot on the primary, a failed read is unavailable and never absent, and an unreadable value is left in place. `SnapshotOutcome.Unreadable` tells unreadable from absent. `IMigrationCache.WriteAsync` and `DeleteAsync` report a write refused before sending (disconnected, token already cancelled, key map or serializer threw) as `NotSent`, an acknowledged one as `Committed`, and any other outcome as `Unknown`, which the router never replays. When the library is unavailable and the source cannot answer, or answers only with an unreadable value, the call throws `CacheUnavailableException`.

## Modes: bypass and draining

`IRouter.Mode` is `Library` or `BypassLibrary`, `ModeReason` says why (`Flag`, `Requested`, `LibraryUnavailable`), and `ModeChanged` is raised once a transition has drained. In `BypassLibrary` every call takes the source path: no library client, no shared-tier hit or fill, no retry on the other client. A write still evicts on this node and, if the library is up, hands its announcement to a bounded background worker, so the call never waits on the library and peers on the library stay coherent (a registration with no local cap announces nothing). Every publish is bounded by the source timeout. A router is in bypass while any of three things holds: the live `UseBypassWhen` setting is true, `EnterBypassAsync` was called and not withdrawn, or the library has not started. The setting is read on every call; an exception counts as true for that call and changes no mode.

Entering: new calls take the source at once, the shared tier is cleared and every mark advanced (a fill that started before is rejected), then the transition waits for calls started in library mode, at most `UseSourceTimeout` (default 30 seconds; give it your old client's timeout). `EnterBypassAsync` returns after that. A late completion from the previous mode never fills the tier.

Leaving: the router waits for every cache's `ITopicSubscriptionState.IsSubscribed` (a topic that does not report it counts as subscribed), then for pending writes to settle. Then new calls take the library, but no shared-tier hit or fill is served until calls started in bypass have ended (same bound) and the tier is cleared again. One deadline of the source timeout covers readiness, settlement and the drain of a leave. If readiness or settlement does not complete in it, the router stays in bypass, logs, counts `leave_timed_out` and tries again after the same time; `LeaveBypassAsync` then throws `TimeoutException`. Once the router has switched to library mode the transition finishes whatever the caller does, so cancelling `LeaveBypassAsync` only keeps the request when it is still waiting. `LeaveBypassAsync` returns when the router is in library mode, or at once if the setting or a missing library still asks for bypass. `ModeChanged` handlers run after the transition's lock is released, in order, so a handler may call back into the router. The old client's own local tier is the application's: turn it on after `ModeChanged` reports bypass and off before calling `LeaveBypassAsync`.

## Library that fails to start

The router owns the whole lifecycle of its library stack: the host does not build or start it (the stack's own hosted service is not registered), so a stack that cannot be built or started never fails the host. Router creation starts the stack in the background and waits at most five seconds, in real time, for it; if it fails or is late, the router starts in `BypassLibrary` with reason `LibraryUnavailable`, logs the exception at error and counts `library_start_failed`. The attempt carries on, retrying after 1 s and doubling to at most 1 min, and when one succeeds the router leaves bypass in the order above. A result that arrives after the router stopped is released, never used, and a factory that hangs delays neither creation nor `DisposeAsync`. Caches are attached all or none: a failure part way gives back the subscriptions and hosted services already taken. With the bypass setting on at start the library is not started until the setting goes off. A setting no start could satisfy (a connection timeout beyond the settle horizon) still fails the host at startup.

## Node identity

The router's source identity, which its events, subscriptions and advertisements carry, is the configured source with a process part added to the host part: `urn:host-p{processId}?stack=UiPath.Caching.Migration`. The default process id is the operating system process id and eight random hex digits, so two processes on one host (an overlapped recycle) are peers and hear each other's events, and so are two routers in one process; `UseNodeIdentity` names it instead. Only the router's named stack changes; the application's own stack and `CacheOptions.MachineUri` keep the host name alone. A Streams topic keeps one consumer group per identity and topic, so each process start adds a group per router topic. A router that stops gracefully (`StopAsync` or `DisposeAsync`) removes its own groups with `XGROUP DESTROY`, best effort and bounded, after its topics are removed. A process that crashes or is killed leaves its groups behind; the application's stream health maintainer removes them once the node counts as departed (see [Broadcast](broadcast.md)), on Redis 7.2 or later for a node whose entry was pruned.

The router keeps its own entry in its stack's node hash (`caching:nodes` under the router stack's key strategy), field `{source identity}#router`, text `kind=router;inst=...;build=...;mig=t1+t2`. The tokens are `byp` (in `BypassLibrary`), `ap=<app>` (the application, from `CacheOptions.AppShortName`, so applications that share one node hash do not count each other's nodes), and, with a pin setting, `pin=<group>` and `sw=<group>`; a reader skips tokens it does not know. The entry is written every `Redis:FormatNegotiation:AdvertiseInterval` of the router's configuration section (15 s by default) and at once on a mode change, stamped with the server's clock, and counts for that section's `LivenessWindow` (2 min by default) plus two intervals; a value that is not positive leaves the router without an entry, logged. A stopping router writes it with `left=1`. Routers prune router entries past the gone age with a compare-and-delete script; where scripts are refused nothing is pruned and readers age stale entries out. The entry's identity and key come from the router's configuration section, bound as the router's stack binds it, never from the library's container, so a library build that hangs or fails does not stop it. Pass `UseSourceConnection(() => sourceDatabase)` so the entry is written over the source client's connection and is kept while the library is down; the delegate must return at once and the database must not add a key prefix of its own. Without it the application's connection carries the entry. A write that fails is logged and retried with backoff (500 ms doubling, at most one interval), never thrown.

Registration checks. Building the router fails when its library stack would change what the application's own client sees. The stack's Redis options are set by the router alone, so their checks (key strategy factory, `CacheKeyStrategy`, `EntryFactory`, `RemoveUnreadable`, `ReadFrom` other than `Master`) catch a library default that changes; the stack inherits the `CacheOptions` of the router's configuration section, so a `DefaultCachePolicy` serializer policy set there is caught too. The startup log lists every library option of the stack. `Exclude(cacheName, reason)` keeps a cache on the application's client and out of the router: locks and other primitives the two stacks implement differently, and map caches the library cannot match. Run `RouterConformance.CheckAsync(services, cacheName, samples)` in CI against a test Redis, with samples for every cached shape including default and empty values: it writes each sample through the source and reads it through the library, then the reverse, and compares the bytes and the deadline of both writes.

Conditional create, versions and nulls. `TryAddAsync` is one atomic create on the client of the group's path (`SET NX` on the library, the source's own conditional create on the source): `Added` evicts, marks and announces like a write, `Exists` changes and announces nothing, `NotSent` on the library is sent on the source, and `Unknown` keeps the key pending as a write of unknown outcome does. A deadline already passed creates nothing. For a cache whose older client puts a type version in its keys, set `Version`; the key map writes the version into the key as before, and the router's events and topic use `{name}@{version}`, so a peer on another version does not hear them, as with the older client. Set `CacheNulls` where the older client reads a stored null as a hit: the source reports it as `new SourceRead<T>(ReadOutcome.Found, null)`, the router serves it from either path and keeps it in the local tier, and a factory does not run for it. A null a factory returns is still not stored.

The older client's channel. Where the older client has its own invalidation channel, pass an adapter with `UseChannelBridge(IChannelBridge)`, so nodes on the older client and nodes on the router hear each other. The router publishes a `BridgeMessage` for every key write, delete and create it commits (`Key`) and for every clear (`Clear`, before and after the scan), with `Origin` set to its identity; carry `Origin` in the old format if it can, so the router drops its own messages. On a received message the router evicts the key (`Key`), the cache's local copies (`Clear`) or every cache's local copies (`Tag`, since the router keeps no tags), and publishes nothing back. The bridge is subscribed when the router starts and works in `BypassLibrary`; `Subscribe` runs off the start path, and one that throws or blocks is counted and retried in the background (1 s doubling to 1 min), never stopping the router or the host; a subscription that arrives after the router stopped is disposed at once, and messages delivered after that are ignored. A publish runs off the caller's thread and is cancelled at the source timeout; at most 16 adapter calls are in flight (`UseChannelBridge(bridge, maxPendingPublishes)`), and a publish beyond that is dropped; `PublishAsync` must not block. Failures (`publish_failed`, `publish_dropped`, `subscribe_failed`, `detach_failed`) are counted under `bridge` and logged once, never thrown, and the local cap bounds how long a peer keeps its copy. The callback the router gives `Subscribe` only evicts and returns at once.

## Precedence

A call is decided by the first of these that applies, and the router logs this order with its settings at startup:

1. Pin (`UsePinWhen`, or a switched group): the library path, never the source.
2. Bypass (the setting, an explicit request, or a library that has not started): source path, no shared tier.
3. The group predicate (`UseLibraryWhen`): library or source; an exception means source, except for a switched group.

## Pin

`UsePinWhen(group => ...)` is a live setting, polled about once a second, that pins a group to the library path. A pinned group ignores bypass and the group predicate and never falls back to the source: a read the library cannot answer throws `CacheUnavailableException` without running the factory, and a write the library did not send is `NotSent`.

- **Acknowledgement.** A node advertises `pin=<group>` only after every call that started before the pin applied (including a library call that fell back to the source) has ended. Withdrawing the setting withdraws the token at once; a node that had acknowledged keeps the source closed (calls are answered unavailable) until its withdrawal is recorded in Redis, in the same step that reads the switch state, and that read shows no switch, since a peer may have read the old acknowledgement. Each node keeps an acknowledgement record per group (`{prefix}mg:{app:group}:ack`, a hash by node field, expiring after a day and refreshed every pass), and a switch is recorded by a script that checks every live node's record is still the one the committing node read, so a withdrawal and a switch cannot both win. The pin needs a Redis that runs scripts; without one it never switches and a withdrawn pin keeps its group unavailable.
- **Switch state.** Once something asks for a format write that needs it (the format negotiation asks the router's gate) and every group of the router is pinned and every live node of the application has the pin, the router records the group as switched in Redis, `{prefix}mg:{app:group}:sw` (no expiry; the prefix is `RedisCacheOptions.KeyPrefix` when `UseSourceConnection` is used, and otherwise the library connection adds it), and only then opens the gate. A switched group is pinned whatever the setting says, so a restart, a library that fails to start, a throwing predicate or `BypassLibrary` leave it on the library or unavailable. A pin alone records nothing, and a recorded switch is not undone.
- **State read.** The state is read before the first call is admitted (at most the start bound) and then every `AdvertiseInterval`, and again after every mode change. A group that is not pinned may take the source only while a read succeeded within three intervals; otherwise, and when the value is not one this version knows, the group is answered unavailable. A call that has fallen from the library asks again before it takes the source, and so does a write that waited on a factory or a lock before it goes to the source, so a state that went stale, a pin that applied or a switch that was recorded meanwhile stops it: the write goes to the library or is not sent.
- **Lost key.** A node that saw the switch writes the key again. A node that restarts with the key missing treats the group as switched when a live router entry of its application reports `sw=<group>`; with no node left that remembers it, a missing key reads as not switched, so keep the pin setting on for a switched group.
- **Format gate.** MessagePack writes stay held, through the format negotiation's own hold, until every group that asks for MessagePack is pinned (with `UseWriteFormatWhen`; without it, every group of the router), every live router entry of the application has `pin=<group>`, every library advertisement has a router entry, this node's own entry is in the list and the switch is recorded against their acknowledgement records. A node without the pin that joins, an incomplete node list, a failed state write or a node list that cannot be read closes it, and a gate that closes even briefly restarts the hold; an unreadable node list keeps the last decision for `FormatNegotiation.MaxViewAge`. The gate applies to the router's envelope too: while it is closed the envelope writes the old format. `IFormatWriteGate` is the seam the library exposes for this.
- **Applications on one hash.** The router stack's node list key has no application part, so applications on one Redis share `caching:nodes`. Entries are told apart by the `ap` token of the router entry (a library advertisement by the router entry of its node), and the state key and gate count only the application's own. An entry that names no application (an older build, or a router with no `AppShortName`) cannot be attributed: it holds the gate and never approves it; two applications with the same `AppShortName` on one Redis are not told apart.
- Group names of a router with a pin setting hold none of `+ @ = { }`. `Clear` still clears through the source client, so a switched group's `Clear` still needs a working source client.

## Write format per group

`UseValueSerializers(stack => stack.AddMessagePackSerializer())` registers value serializers in the router's own stack (the application's registrations are not seen there), and `UseWriteFormatWhen(group => ...)` is a live setting read on every library write: `"messagepack"`, `"json"` or `null` (`json`). Both need `UsePinWhen`, and `UseWriteFormatWhen` needs `UseValueSerializers`; registration fails otherwise.

- **Envelope until ready.** `"json"` writes the older client's envelope. `"messagepack"` writes MessagePack only while the group is pinned, acknowledged and switched, and the gate is open; in every other case the group writes the envelope. The library's own negotiation still applies beneath: a node that joins without the pin or the format turns the write back to the envelope on the next write, and with `UseWriteFormatWhen` the stack's `FormatNegotiation` timings come from the router's configuration section, the one the pin validates (a router without it keeps the stack's defaults).
- **No switch during a key move.** While a group's keys move (key move state Preparing to Copied, in either direction), a group that has not switched yet keeps its format: a write that asks for `"messagepack"` writes the envelope and does not ask for the switch, so promoters, the mover and a reverse never meet the in-place keys in two formats. Each such write counts `format_switch_held` (tags `group` and `pending`), and the first one raises the key move alert `format_switch_held` with the pending format. A node also holds a group of its key move registration until it has read that group's state, so a node that restarts in the middle of a move cannot switch before it knows. Once the state is Off or Done, the next write asks for the switch again, with no restart. A group that switched before its move started keeps its format.
- **Gate over the groups that ask.** The gate is one for the stack, so a group that asks for MessagePack waits for every other group that asks, and a group that does not ask (`json`, `null`, a name that is not known, or a setting that throws, which clears the group's asking at once) holds nothing, is never recorded as switched, and may stay unpinned. A group counts from its first write that asked for MessagePack, and stops counting at the next pass after its setting goes back. The switch of each asking group is recorded separately.
- **Fail closed.** A setting that throws or answers a name other than `messagepack`, `json` or `null` writes the envelope and is logged once per group; the group stops counting, as for `json`, until its setting answers `messagepack` again.
- **Reads.** A read of a group that does not ask for MessagePack, or is not applied, acknowledged, switched and durable, carries the envelope policy, so a `MigrateOnRead` in the stack's default policy never rewrites it.
- **Back to json.** Setting a group back to `json` writes the envelope on the next write. Converted values stay MessagePack and still read; the group does not go back to the older client, since a switched group stays on the library path.
- Converting values already stored, and telling when the conversion is complete, are not part of this setting.

## Telemetry

Meter `UiPath.Caching.Migration`, counters `local_hit`, `redis_hit`, `miss`, `factory_runs`, `unavailable`, `unreadable`, `publish_failed` and `pending`, each tagged `cache`, `group`, `path` and `path_reason` (`flag`, `predicate_error`, `bypass`, `bypass_flag_error`, `library_unavailable`, `other_client_read`, `other_client_unreadable`, `pin`, `pin_state_unknown`). `mode_change` (tags `mode`, `reason`) counts completed transitions and `library_start_failed` counts failed starts. `format_switch_held` (tags `group`, `pending`) counts a write that kept its format because the group's keys move.

Meter `UiPath.Caching.KeyMove` includes `cache.keymove.gate_overrides` (tags `group`, `gate`), which counts each gate bypassed by an approval when the transition completes, and `cache.keymove.canary_keys` (tag `group`), which counts keys each inventory pass finds were written after all nodes stopped writing to the source side.

## Key move stage checks

Use these check IDs to identify the missing evidence when a stage is blocked or an instance move holds admission.

| IDs | What they check |
| --- | --- |
| `start.km_support`, `start.pins`, `start.node_list`, `start.foreign_node` | Fresh nodes support key move, pin the group without bypassing, form a complete list, and belong to the same scope. |
| `start.release_floor`, `start.view_stable`, `start.snapshot_freshness` | The minimum release is attested, the node views have held steady, and advertised snapshots are fresh. |
| `start.dry_run`, `start.memory_headroom`, `start.format_settled` | The dry run is recent, the memory estimate leaves enough headroom, and the format is settled. |
| `start.group_listed`, `start.server_preflight`, `start.cache_set`, `start.native_empty` | All nodes list the group, Redis passes preflight, the registered cache sets agree, and the masters find no owned native keys. |
| `start.claim_available`, `start.binding` | Groups that require a move claim have a claim provider configured, and fresh nodes advertise support for marker binding. |
| `close.acks`, `close.soak`, `close.canary`, `close.consent` | Every fresh node acknowledges the identity, the soak has elapsed, no canary activity occurred during it, and consent covers the stored residue. |
| `close.node_readiness`, `close.inventory`, `close.views` | Fresh nodes can use key move without bypassing, current residue fits within the approved counts, and all views confirm the close stage. |
| `close.in_place_readers` | Close requires `AttestInPlaceReadersDeployed(group, evidenceId)` in the builder configuration. Until then, it emits `close_pending` with detail `close.in_place_readers:in_place_readers_not_attested`. No approval overrides this gate. |
| `drain.confirming_pass`, `drain.skipped_accounted`, `drain.promotions_idle`, `drain.canary_zero` | The confirming pass finds nothing movable, all skips are accounted for, no promotions remain in flight, and the forward canary is zero. The first two IDs are reported together because the mover supplies one verdict for both. |
| `dst_preflight`, `dst_state_missing`, `dst_unreachable`, `dst_preflight_timeout`, `dst_not_master`, `dst_replica_unhealthy` | Before updating the source control record, the destination state and masters must answer within the timeout, and known replica counts must meet the configured expectation. |
| `baseline_unavailable`, `pend_wait_unavailable`, `mirror_open_unavailable` | The controller could not establish or confirm the generation baselines, the destination mirror pend, or the destination mirror open. |
| `src_admission_pending`, `mirror_repair_pending` | Source admission needs fresh mirror evidence that the move ended. Destination admission or commit needs a mirror confirmed in the current destination generation. |

Approval commands take approval kinds. `start` supplies the release attestation. `start_unsettled` requires the exact `UpgradeHoldOverrideText` confirmation. `start_no_dry_run`, `start_memory`, and `control_records_evictable` authorize their respective exceptions. Either `close` or `close_force` attests that the source application code remains deployed and approves the stored residue. `close_force` also permits proceeding before the soak or with canary activity. `force_reverse` can override the key move support, pin, node list, and snapshot checks for reversal. An active hold blocks a forward drain.

To run a move step by step, with the approvals, confirm texts and rollback paths, see [Operating a key move](key-move.md).
